## 1. Resumo

- **Problema:** os próximos itens do M1 (schema + migrations, Better Auth, REST de trips e o spike do `Bun.sql`) precisam de um Postgres real. O `development.md` §2 proíbe mock de banco em testes de integração, que rodam contra Postgres e Redis "from the compose file". O `planner.md` §8 pede que "Docker Compose (Postgres, Redis) is up before the code whose tests need it".
- **Objetivo:** um comando sobe Postgres 18 e Redis 8 locais, com a configuração prevista para produção (`deploy.md` §3), prontos para desenvolvimento e para testes de integração.
- **Resultado esperado:** `bun run infra:up` sobe os dois serviços saudáveis, `bun run infra:check` confirma a configuração e `bun run infra:down` derruba.

## 2. Estado atual

**Confirmado na máquina e no repositório (2026-10-24):**

- Não existe a pasta `infra/`. Este plano ainda não está commitado: entra como primeiro commit da branch (C0).
- Docker 29.9.2 e Docker Compose v5.6.1 estão instalados, com o daemon ativo. O Podman 5.8.9 também está instalado.
- **A porta 5432 do host já está ocupada** por um container `postgres-18` (`postgres:18-alpine`) de fora do projeto. A 5433 e a 6380 estão livres.
- O kernel local usa **páginas de 16 KB** (Asahi, aarch64). A produção (Hetzner CAX) e o runner ARM do GitHub usam páginas de 4 KB.
- O `.github/scripts/affected-areas.sh` só detecta áreas por workspace (`turbo ls --affected`). A pasta `infra/` não é workspace, então o job `infra` precisa de outra regra (P6).

**Verificado em spikes (2026-10-24, containers temporários com `--rm`, nada no repositório):**

- **Redis:**
  - `redis:8` é o Redis 8.10.2, com jemalloc 5.3.0. A imagem e a tag exata `redis:8.10.2` existem para arm64.
  - **Roda com páginas de 16 KB:** 141 MB alocados e mais de 126 mil chaves sem abort do jemalloc.
  - Com `--maxmemory 256mb --save "" --appendonly no`, `CONFIG GET` devolve `268435456`, `save` vazio e `appendonly no`.
  - A imagem carrega módulos (JSON, Search, Bloom, TimeSeries). Eles não atrapalham e ficam como estão.
  - O Redis avisa que `vm.overcommit_memory` está desligado. Isso é coisa do host de produção: anotado no `deploy.md` §6 para o `cloud-init` (M5), fora deste plano.
- **Postgres:**
  - `postgres:18` é o PostgreSQL 18.6 (Debian), e a tag exata `postgres:18.6` existe.
  - A imagem declara `VOLUME /var/lib/postgresql`, com `PGDATA=/var/lib/postgresql/18/docker`. O volume é montado em `/var/lib/postgresql`.
  - Um `postgresql.conf` mínimo passado com `-c config_file=` funciona: `uuidv7()`, `max_connections=50`, `shared_buffers=256MB` e `effective_cache_size=1GB`. O fuso fica `GMT` (UTC), o que serve.
  - **`/dev/shm` padrão (64 MB) quebra queries paralelas:** um parallel hash join sobre 4 milhões de linhas falha com `could not resize shared memory segment ... No space left on device`. Com `--shm-size=256m`, a mesma query passa, com um hash de cerca de 185 MB num batch (P8).
  - **O servidor temporário do init escuta só no socket:** o entrypoint o sobe com `-c listen_addresses=''` (linha 297 do `docker-entrypoint.sh`). Um `pg_isready` pelo socket pode responder "pronto" antes do servidor final, e pelo TCP não (P9).

**Decisões documentadas que se aplicam:**

- **`deploy.md` §3:** `postgres:18` com `max_connections=50`, `shared_buffers=256MB` e `effective_cache_size=1GB`; `redis:8` com `maxmemory 256mb`, `save ""` e `appendonly no`.
- **`deploy.md` §2:** em produção, Postgres e Redis ficam na rede interna, **sem porta publicada**.
- **`deploy.md` §7 e §12:** `infra/compose.yml` (serviços base e redes) + `infra/compose.dev.yml` (portas, mailpit, toxiproxy e Caddy local); `infra/postgres/postgresql.conf`.
- **D28:** `DEFAULT uuidv7()` no banco, o que exige o Postgres 18. **D30:** pool de 10 conexões por instância, dentro de `max_connections=50`.

**A verificar na implementação:**

- O compose lê o `.env` do diretório do projeto, que por padrão é a pasta do primeiro arquivo (`infra/`). Confirmar no C1 que uma porta definida em `infra/.env` é respeitada.

## 3. Requisitos e critérios de aceitação

1. **Subir:** `bun run infra:up` (`docker compose -f infra/compose.yml -f infra/compose.dev.yml up -d --wait`) sobe o Postgres e o Redis e só retorna depois que os healthchecks passam. O healthcheck do Postgres usa TCP (P9).
2. **Postgres:**
   - `SELECT uuidv7()` funciona;
   - `SHOW max_connections` devolve 50;
   - `SHOW shared_buffers` devolve 256MB;
   - `/dev/shm` tem 256 MB (P8).
3. **Redis:**
   - `PING` devolve `PONG`;
   - `CONFIG GET maxmemory` devolve 256 MB;
   - `save` está vazio e `appendonly` é `no`.
4. **Verificação única (P7):** `bun run infra:check` roda as verificações dos itens 2 e 3 contra os serviços no ar e falha se alguma não bater. A CI e o desenvolvimento local usam o mesmo script.
5. **Persistência:**
   - os dados do Postgres sobrevivem a `infra:down` seguido de `infra:up` (volume nomeado);
   - `bun run infra:reset` (`down -v`) apaga os dados;
   - o Redis não guarda nada entre reinícios.
6. **Portas:** só o overlay de dev publica portas, e só em `127.0.0.1`. O `compose.yml` base não publica nenhuma porta, como em produção.
7. **Portas configuráveis:** as portas do host vêm de variáveis de ambiente, com padrões que não conflitam com a 5432 ocupada (P2).
8. **Sem banco de testes no compose (P3):** o compose sobe só o banco `caravan`. Quem cria o `caravan_test`, no mesmo container, é o harness de teste do item "schema + migrations".
9. **Versões exatas (P11):** `postgres:18.6` e `redis:8.10.2`.
10. **Sem segredos no repositório:** as credenciais de dev são fixas e óbvias, e ficam só no overlay de dev. O `infra/.env.example` documenta as variáveis que podem ser sobrescritas.
11. **Documentação (P12):**
    - a seção "Commands" do `AGENTS.md` inclui `infra:up`, `infra:down`, `infra:reset` e `infra:check`;
    - o `deploy.md` §3 inclui o `shm_size`;
    - o `deploy.md` §7 diz o que o compose de dev sobe hoje.

## 4. Proposta

**Arquivos:**

- **`infra/compose.yml`:**
  - `name: caravan`, para que os volumes se chamem `caravan_*`;
  - serviços `postgres` (`postgres:18.6`) e `redis` (`redis:8.10.2`), com tag exata e sem digest (P11);
  - healthchecks: `pg_isready -h 127.0.0.1 -U $$POSTGRES_USER -d $$POSTGRES_DB` (P9) e `redis-cli ping`;
  - `shm_size: 256mb` no Postgres (P8);
  - rede interna e o volume `pgdata`, montado em `/var/lib/postgresql`;
  - nenhuma porta publicada.
- **`infra/compose.dev.yml`:**
  - portas `127.0.0.1:${CARAVAN_POSTGRES_PORT:-5433}:5432` e `127.0.0.1:${CARAVAN_REDIS_PORT:-6380}:6379`;
  - credenciais de dev (`caravan`/`caravan`, banco `caravan`) via variáveis com valor padrão.
- **`infra/postgres/postgresql.conf`:**
  - só o que difere do padrão: `listen_addresses = '*'`, `max_connections = 50`, `shared_buffers = 256MB` e `effective_cache_size = 1GB`;
  - os valores são os do CAX11, que a produção usa no começo. Os do CAX21 ficam para o `compose.prod.yml` (P10);
  - é montado no container e passado com `-c config_file=...`.
- **Sem script de init para o banco de testes (P3):** um script de init só rodaria quando o volume fosse criado. O harness de teste do item "schema + migrations" cria o `caravan_test` se ele não existir e aplica as migrations, tanto num volume novo quanto num já existente, e também na CI.
- **Redis:** a configuração vai em `command` (`redis-server --maxmemory 256mb --save "" --appendonly no`). Nada além do que o `deploy.md` §3 define.
- **`infra/check.sh` (P7):**
  - roda as verificações de §3, itens 2 e 3, com `docker compose ... exec -T` (`psql` e `redis-cli`), dentro dos containers;
  - imprime cada verificação e sai com erro na primeira divergência;
  - não testa persistência (`down`/`up` e `reset`), porque isso destrói dados. A persistência é verificada à mão no C2 e no C3.
- **`infra/.env.example`:** documenta as portas e as credenciais. O compose lê o `.env` da pasta do primeiro arquivo, que é `infra/`.
- **Scripts na raiz:** `infra:up`, `infra:down`, `infra:reset` e `infra:check`.

**CI (P4 e P6):**

- **Detecção da área (P6):**
  - o `affected-areas.sh` ganha um segundo mapa, de áreas por caminho, ao lado do mapa por workspace: `declare -A path_areas=([infra]='^infra/')`;
  - num PR, a área fica `true` se algum arquivo do `git diff "$base...HEAD"` casar com o regex. Num push no `master`, ou quando a configuração da raiz ou a própria CI mudam, roda tudo, como hoje;
  - o job `changes` expõe o output `infra`, e o job `ci` ganha `infra` no `needs`;
  - descartada: a action `dorny/paths-filter`, que seria mais uma dependência externa e uma segunda fonte de verdade.
- **Job `infra`, como mais uma área do modelo de CI do [`1.monorepo.md`](./1.monorepo.md). Passos:**
  1. `docker compose ... config -q`;
  2. `up -d --wait`;
  3. `infra/check.sh` (P7);
  4. `down -v`, com `if: always()`.
- Quando vierem os testes de integração, os jobs de área vão usar os mesmos arquivos de compose, em vez de `services:` do GitHub Actions. Assim a configuração tem uma fonte só.

## 7. Riscos e dependências

| Risco | Mitigação |
|---|---|
| Porta 5432 já ocupada no host (confirmado) | Portas padrão 5433 e 6380, configuráveis por variável (P2) |
| `/dev/shm` de 64 MB quebra queries paralelas (reproduzido no spike) | `shm_size: 256mb` no compose base, que vale também para a produção (P8) |
| Healthcheck do Postgres passar durante o init (confirmado no entrypoint) | `pg_isready` pelo TCP (P9) |
| Versões fixas ficarem velhas | Atualização manual por enquanto; Renovate ou Dependabot ficam fora do escopo (P11) |
| Credenciais de dev chegarem à produção | Ficam só no `compose.dev.yml`; o futuro `compose.prod.yml` vai exigir as variáveis sem padrão (`${POSTGRES_PASSWORD:?}`) |
| Testes poluindo os dados de desenvolvimento | Banco `caravan_test` separado no mesmo container, criado pelo harness de teste no item "schema + migrations" (P3). No Redis, o pub/sub ignora o índice de banco, então o isolamento dos testes que usarem Redis fica para quando o primeiro deles for escrito |
| Podman no lugar do Docker | Fora do escopo: o suporte é ao Docker, que é o daemon ativo na máquina |
| `bun install --frozen-lockfile` em Dockerfile (observação do dono do projeto) | Não se aplica aqui: este plano só usa imagens oficiais, sem Dockerfile próprio |

## 8. Decisões

- **P1. Mesmo PR ou PR separado?** **decidido (2026-10-24):** PR separado, só com o Docker Compose, na branch `chore/docker-compose`, criada depois do merge do PR do `1.monorepo.md`. Cada revisão fica menor, e a CI do `1.monorepo.md` já existe para validar o job `infra`.
- **P2. Portas do host:** **decidido (2026-10-24):** 5433 (Postgres) e 6380 (Redis), configuráveis pelo `infra/.env`.
- **P3. Banco de testes:** **decidido (2026-10-24): opção A**, o `caravan_test` como outro banco no mesmo container do `caravan`. Quem cria o banco é o harness de teste do item "schema + migrations", que também aplica as migrations. O compose não tem script de init. O isolamento dos testes que usarem Redis fica para o primeiro deles.
  - Descartadas: um container só para testes (B) e um banco novo por execução (C). A opção C pode ser acrescentada sobre a A se os testes ficarem lentos.
- **P4. Job `infra` na CI:** **decidido (2026-10-24):** sim.
- **P5. Teste de migrations:** **decidido (2026-10-24):** fica para o plano do item "Database schema + migrations (Drizzle)", que vai cobrir três verificações:
  1. as migrations aplicam do zero num banco vazio;
  2. o schema do Drizzle e as migrations batem (alterar o schema sem gerar a migration faz a CI falhar);
  3. as migrations são só aditivas (`DROP`, `RENAME` ou mudança de tipo fora de uma fase de contração marcada fazem a CI falhar), conforme o `deploy.md` §5 e a decisão P7 do `deploy.md`.

  A compatibilidade com o código da release anterior fica fora: já está prevista para o M5.
- **P6. Detecção da área `infra` na CI:** **decidido (2026-10-24):** um mapa de áreas por caminho no `affected-areas.sh` (`[infra]='^infra/'`), ao lado do mapa por workspace. O job `changes` expõe `infra`, e o job `ci` depende dele. A verificação de que um PR sem `infra/` pula o job fica para o PR seguinte (C4).
  - Descartada: a action `dorny/paths-filter`.
- **P7. Verificação única:** **decidido (2026-10-24):** `infra/check.sh`, chamado pelo script `infra:check`, com as verificações de §3, itens 2 e 3. A CI e o C2/C3 usam o mesmo script. A persistência fica fora do script, porque destrói dados.
- **P8. `shm_size` do Postgres:** **decidido (2026-10-24):** `shm_size: 256mb` no `compose.yml` base. É o único ajuste além do `deploy.md` §3, justificado pelo spike de §2, e o `deploy.md` §3 passa a registrá-lo (C5).
- **P9. Healthcheck do Postgres:** **decidido (2026-10-24):** `pg_isready -h 127.0.0.1 -U $$POSTGRES_USER -d $$POSTGRES_DB`, pelo TCP, para não passar durante o servidor temporário do init.
- **P10. `postgresql.conf` de dev e de produção:** **decidido (2026-10-24):** o arquivo guarda os valores do CAX11, que valem para dev e para o começo da produção. Os valores do CAX21 (`deploy.md` §3) ficam para o `compose.prod.yml` (M5), por `-c` ou por um arquivo à parte.
- **P11. Fixação das versões:** **decidido (2026-10-24):** tag exata sem digest, `postgres:18.6` e `redis:8.10.2`. Atualização automática (Renovate ou Dependabot) fora do escopo.
- **P12. Escopo da documentação (C5):** **decidido (2026-10-24):** além das portas, o `deploy.md` §7 ganha uma nota sobre o que o compose de dev sobe hoje (só Postgres e Redis; Caddy, api, web, mailpit e toxiproxy chegam nos milestones previstos), e o §3 ganha o `shm_size`.
