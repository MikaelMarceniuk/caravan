## 1. Resumo da feature

- **Problema:** depois do login a pessoa cai em `/session`, uma página provisória (B10 do plano 4). A API não tem viagens, e o M1 só termina com "o login e a lista de viagens no ar". O M2 também precisa de viagens com membros, porque o pipeline de ops lê o papel do membro dentro da transação (§6).
- **Objetivo:**
  - **API:** `POST /api/trips` e `GET /api/trips`, só com sessão, com o body validado pelo `t` (TypeBox) do Elysia (`development.md` §2, API; D29 revisado);
  - **banco:** tabelas `trips` e `trip_members` na migration `0001_trips`;
  - **web:** `/trips` no lugar de `/session`, com a lista em abas Upcoming/Past, o diálogo "Plan a new trip" (só o nome) e um menu do usuário com "Sair";
  - **docs:** a decisão do open-topics item 2 (datas derivadas das paradas) registrada como D44, com tudo o que ela muda na arquitetura, e as convenções do REST (códigos de erro, macro de sessão, respostas embrulhadas) como D45. O TypeBox nos bodies já está no `development.md` e no D29 (revisão 3).
- **Resultado esperado:**
  1. A pessoa entra e cai em `/trips`, que mostra as viagens das quais ela é membro.
  2. Ela abre "New trip", digita um nome e cria a viagem: o diálogo fecha e a viagem aparece em Upcoming, com "No stops yet".
  3. Outra pessoa não vê essa viagem, e nenhuma rota de viagem responde sem sessão.
  4. A CI falha se o schema mudar sem migration (o teste que já existe).

### Datas: o que muda com a decisão A (D44)

- `Trip` passa a ser `id, name, ownerId`; **as datas são derivadas**: da primeira chegada à última saída das paradas não apagadas, e `null` sem paradas.
- Saem do domínio:
  - o invariante "as paradas ficam dentro das datas da viagem" e o `RejectReason` `outside_trip`;
  - o campo `dates` do `trip.update`;
  - a regra "um `trip.update` que deixa paradas de fora vira aviso";
  - a linha "assimetria das datas" do §19.
- **Gap** passa a ser "datas entre duas paradas sem nenhuma parada", e não mais "datas da viagem sem parada".
- O `EmptyTrip.png` ("14 nights to plan") e os campos Starts/Ends do `NewTrip.png` deixam de valer (§17).
- **No M1** nenhuma viagem tem paradas, então a API ainda não manda `dates`. O M2, com `stops`, acrescenta `dates: { start, end } | null` ao resumo (mudança aditiva, P7), e só então o web separa por data (§8, C2).

### API

- **Sessão:** um plugin `session.ts` com uma `macro` do Elysia. Uma rota com `{ traveler: true }` resolve `auth.api.getSession({ headers })`; sem sessão, devolve `status(401, { code: 'UNAUTHORIZED' })`, e com sessão entrega `traveler` (`id`) ao handler. O M2 (`/ws-ticket`) e o M4 reaproveitam o plugin.
- **Validação (TypeBox, `development.md` §2):** `body: t.Object({ name: t.String({ minLength: 1, maxLength: TRIP_NAME_MAX }) })`, com o limite vindo do `core`. Um hook `transform` da rota tira os espaços das pontas de `body.name` (quando é string) antes da validação, então "   " vira "" e é recusado, e o limite de 120 vale para o nome limpo. Um `onError` no plugin de viagens troca `VALIDATION` (422) e `PARSE` (400) por `{ code: 'INVALID_INPUT' }`, porque a API manda códigos e não texto (D34). Se o `transform` não se comportar como esperado, o plano B é `t.String({ pattern: '\\S' })` mais o trim no handler (§7).
- **Onde ficam as regras:** o limite (`TRIP_NAME_MAX`) e o tipo da resposta (`TripSummary`) ficam no `core`, para API e web usarem os mesmos; o schema do body fica na rota (TypeBox), e o do formulário no web (Zod, com as chaves do `next-intl`). O `core` **não** ganha `zod` neste item; ele chega com as ops do M2.
- **`@sinclair/typebox`** passa a ser dependência explícita da API, fixada em 0.34.52 (a versão do lockfile), como o D39 faz com o resto da stack. Hoje ela só entra como peer do Elysia.
- **Criação:** `db.transaction`: `INSERT trips (name, owner_id) RETURNING id, name` e `INSERT trip_members (trip_id, user_id, role='owner')`. Nenhuma linha em `ops_log` (que ainda não existe); a viagem nasce na versão 0, como diz o §13.
- **Lista:** `trip_members JOIN trips WHERE user_id = $1 ORDER BY trips.created_at DESC, trips.id DESC`, devolvendo `{ id, name }`.
- **Contrato:** `TripSummary = { id: string (uuid), name: string }`; as respostas vêm embrulhadas (`{ trips }`, `{ trip }`) para crescer sem quebrar. Sem schema de resposta na rota: a resposta é montada pelo próprio handler a partir do banco.

### Banco (`0001_trips`)

```
trips         id uuid PK DEFAULT uuidv7(), name text NOT NULL, owner_id uuid NOT NULL → user(id),
              created_at timestamptz NOT NULL DEFAULT now()
trip_members  trip_id uuid NOT NULL → trips(id) ON DELETE CASCADE, user_id uuid NOT NULL → user(id),
              role text NOT NULL ('owner' | 'editor', tipado no TS como o `locale`),
              joined_at timestamptz NOT NULL DEFAULT now(),
              PK (trip_id, user_id), índice trip_members_user_id_idx (user_id)
```

- **Ficam para depois, todas aditivas (P11):** `current_version NOT NULL DEFAULT 0` e `deleted_at` (M2, pipeline e `trip.delete`), `color` e `last_seen_at` (M4, membros e presença). Assim segue o D38: nada antes da hora.
- **FKs para `user` sem cascade:** apagar uma conta passa as viagens adiante (§18); isso é lógica de aplicação e ainda não existe.
- **`owner_id` e `role = 'owner'`** guardam o mesmo fato, como no §11. Os dois só mudam juntos (transferência de dono, M4).

### Web

- **`/trips`:** um server component lê a sessão, hidrata `['session']` e renderiza `TripsScreen`. A lista vem pelo cliente, com `useTrips()` (`['trips']`), e tem estado de carregando e de erro. Prefetch da lista no servidor é a alternativa (C7).
- **Abas:** `Tabs` do shadcn/Radix. Upcoming vem selecionada, e as contagens ficam no nome acessível. No M1 a regra é "sem datas → Upcoming", então tudo vai para Upcoming e Past mostra o estado vazio. A regra por data entra no M2 com o campo `dates` (C2).
- **Card:** `article` com `h2` (o nome) e "No stops yet". Não é link enquanto não houver página da viagem (M2); fica sem relativo ("IN 3 WEEKS"), datas, barra de paradas, avatares e presença, que dependem de dados que ainda não existem.
- **Diálogo:** `Dialog` do shadcn (Radix: prende o foco, fecha com `Esc`, devolve o foco), em tela cheia no celular. Dentro dele, um `Form` com `FormTextField name` e o `SubmitButton` "Create trip", além de Cancel e "You'll be the owner.". Saem do design, até as features chegarem: Starts/Ends (decisão A), First stop (M2) e Invite people (M4).
- **Depois de criar:** `useCreateTrip` invalida `['trips']`, o diálogo fecha, um toast "Trip created" é anunciado e o foco volta ao botão que abriu.
- **401:** `useTrips`/`useCreateTrip` com 401 gravam `null` em `['session']`, e o efeito que já existe leva para `/sign-in`.
- **Header:** logo + `UserMenu` (`DropdownMenu`: iniciais, nome, email e "Sign out"). A busca ⌘K e o seletor de idioma ficam de fora.
- **Tipos e limites:** `TripSummary` e `TRIP_NAME_MAX` vêm do `@caravan/core` (D42; o tipo é um `type` TS, não mais um `z.infer`). O web passa a depender de `@caravan/core` e o inclui em `transpilePackages` (D36). O schema Zod do formulário fica em `src/lib/schemas/trip.ts`, como os de auth (R2 do plano 4).

### Alternativas consideradas

- **Datas próprias (B):** descartada pelo dono do projeto. A primeira parada no NewTrip já no M1 também, porque puxaria `stops`, `Place` e Photon para o M1, fora do pipeline.
- **Só `trips.owner_id`:** descartada. O M2 teria que fazer backfill dos donos e mudar a consulta da lista.
- **Rota em Server Action/route handler do Next:** proibida (§12: toda regra passa pela API).
- **Zod no body das rotas (D29 original):** substituído pelo TypeBox a pedido do dono do projeto (D-G). Um schema Zod no `core` daria uma fonte só para API e web; com o TypeBox, a fonte comum passa a ser a constante `TRIP_NAME_MAX`, e as duas validações (rota e formulário) são testadas cada uma no seu seam.
- **Testes unitários no `core`:** sem schema, o `core` só tem uma constante e um tipo, e não há comportamento para testar ali. Os limites são testados no seam REST e no formulário (C4).

## 7. Riscos e dependências

| Risco | Mitigação |
|---|---|
| O hook `transform` não tira os espaços antes da validação do `t` (ou o `onError` não troca o corpo do erro) | Confirmar em T4; plano B: `t.String({ pattern: '\\S', maxLength })` e o trim no handler, registrado no doc da feature |
| Duas validações do mesmo nome (TypeBox na rota, Zod no formulário) podem divergir | Os dois usam `TRIP_NAME_MAX` do `core`, e cada um tem testes no seu seam com os mesmos casos (vazio, só espaços, 120, 121) |
| TypeBox e Zod convivem no repo (D29 dizia "uma biblioteca só") | Fronteira explícita no `development.md` §2: TypeBox no body das rotas; Zod no resto. Sem regra do Biome, depende de revisão (P2) |
