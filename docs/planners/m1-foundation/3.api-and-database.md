## 1. Resumo da feature

- **Problema:** os próximos itens do M1 (Better Auth, REST de trips, deploy mínimo e o spike do `Bun.sql`) precisam de uma API rodando e de um banco acessível pelo Drizzle. Hoje não existe `apps/api`, nem Drizzle, nem banco de testes. O `deploy.md` §3 já prevê `/healthz` e `/ready`.
- **Objetivo:**
  - criar o app `apps/api` com **Elysia**, `/healthz` e `/ready`;
  - deixar o **Drizzle configurado** (cliente da aplicação, `drizzle.config.ts`, pasta de schema e `db:generate`) e o harness do `caravan_test`;
  - **sem tabelas e sem migrations agora** (Q3). Cada feature cria as suas tabelas, na sua própria migration, quando for desenvolvida. A primeira migration, o `db:migrate` e os três testes de migrations entram com o item de auth, junto com as tabelas do Better Auth (§10).
- **Resultado esperado:**
  - `bun run --filter @caravan/api dev` sobe a API; `GET /healthz` responde 200; `GET /ready` responde 200 com o Postgres no ar e 503 sem ele;
  - `bun run --filter @caravan/api db:generate` funciona e, sem tabelas, diz que não há mudanças;
  - os testes da API criam o `caravan_test` sozinhos e o apagam no fim de cada arquivo de teste (Q4);
  - a CI roda os testes da API contra o Postgres do compose.

## 4. Proposta arquitetural

**Estrutura:** `apps/api` com Elysia, só com o que este item precisa. Os módulos de domínio do §13 (`auth/`, `trips/`...) entram com as suas features.

```
apps/api/
  package.json            @caravan/api · scripts: dev, start, lint, typecheck, test, db:generate
  tsconfig.json           types: ["bun"] · include: src, drizzle.config.ts
  __tests__/tsconfig.json
  biome.json              root: false, extends "//"
  drizzle.config.ts       dialect postgresql · schema ./src/db/schema · out ./src/db/migrations · casing snake_case
  .env.example            DATABASE_URL=postgres://caravan:caravan@127.0.0.1:5433/caravan · PORT=3000
  src/
    index.ts              entrada: lê PORT e DATABASE_URL, cria o db e chama createApp(...).listen(PORT)
    app.ts                createApp({ db }): monta o Elysia com as rotas; não abre porta
    health/routes.ts      GET /healthz e GET /ready
    db/
      client.ts           createDb(url): Drizzle sobre Bun.sql, pool de 10 (D30), casing snake_case
      schema/index.ts     vazio agora; cada feature acrescenta seu arquivo (auth.ts, trips.ts...) e o re-exporta
  __tests__/
    support/test-database.ts   harness do caravan_test (Q4)
    health/routes.test.ts      /healthz e /ready via app.handle
```

A pasta `src/db/migrations/` não existe neste item: ela nasce com o primeiro `db:generate` que encontrar uma tabela, no item de auth.

**API (Elysia):**

- **Versão (Q14):** a `latest`, hoje **1.4.30**, com versão exata.
- **`createApp({ db })` separado do `index.ts`:**
  - os testes montam o app de verdade e o exercitam pelo seam REST (`app.handle(new Request(...))`, H3), sem abrir porta;
  - o `db` entra como parâmetro porque é a única configuração que o teste precisa trocar: o `caravan_test`, ou uma URL onde nada escuta (para o 503);
  - não é uma porta nova da arquitetura nem uma abstração para mock: é o mesmo cliente Drizzle real.
- **`/healthz`:** não toca no banco; é o "processo vivo" do `deploy.md` §3.
- **`/ready`:** um `SELECT 1` pelo `db` da aplicação. Qualquer erro vira 503 `{ "status": "unavailable" }`. O Redis entra no `/ready` junto com o primeiro código que usar Redis (Q12). O "503 durante o shutdown" fica para o graceful shutdown, no item de deploy.
- **Respostas:** só códigos (`ok`, `unavailable`), nunca texto de UI (AGENTS.md, Language).
- **Configuração:** `PORT` (padrão 3000) e `DATABASE_URL` (obrigatória, Q8). Checagem manual no `index.ts`, sem Zod por enquanto: o Zod (D29) entra com a primeira rota que valida entrada.
- **Scripts:** `dev` = `bun --watch src/index.ts`; `start` = `bun src/index.ts`. O binário compilado (`bun build --compile`) fica para o deploy.

**Banco (Drizzle):**

- **Versão (Q2):** a estável, `drizzle-orm` 0.45.4 + `drizzle-kit` 0.31.11, com versão exata (`bunfig.toml`).
- **Cliente da aplicação:** `createDb(url)` com `drizzle-orm/bun-sql`, pool de 10 (D30) e `casing: 'snake_case'` (Q9): TypeScript em camelCase e banco em snake_case, como no §11. A espera de 2 s por conexão (`busy`) e o timeout de 5 s por transação continuam no spike do D30.
- **`drizzle.config.ts`:** com o mesmo `casing`, para o `drizzle-kit` gerar os nomes iguais aos do cliente.
- **`drizzle-kit` é só dev dependency**, para `generate`. Sem `drizzle-kit migrate`/`push`: eles exigem o driver `pg` ou `postgres`. Quem vai aplicar as migrations é o migrator do Drizzle sobre `Bun.sql`, no item de auth (§10).
- **Banco de testes (Q4):**
  - o harness é um módulo que o arquivo de teste chama explicitamente; ele registra um `beforeAll` e um `afterAll`;
  - no `beforeAll`: conecta no banco de `DATABASE_URL` (o `caravan`, com o mesmo usuário), roda `DROP DATABASE IF EXISTS caravan_test WITH (FORCE)` (limpa o que sobrou de uma execução interrompida) e `CREATE DATABASE caravan_test`, e entrega o `db`;
  - no `afterAll`: fecha o pool e roda `DROP DATABASE caravan_test`;
  - quando houver migrations (item de auth), o `beforeAll` as aplica logo depois do `CREATE`;
  - o isolamento **entre testes do mesmo arquivo** fica para o primeiro teste que gravar dados (auth), quando dá para medir o custo das opções (Q4).

**Configuração e ferramentas:**

- **`DATABASE_URL` (Q8):** obrigatória em todo lugar, sem valor padrão no código:
  - no `index.ts`, a API não sobe sem ela;
  - nos testes, o harness falha sem ela, com a mensagem de §3, item 6;
  - localmente, vem do `apps/api/.env`, copiado do `.env.example` (o Bun carrega o `.env` sozinho); na CI, do `env` do job.
- **Turbo:** a tarefa `test` declara `env: ["DATABASE_URL"]` (o modo estrito do Turbo 2 filtra variáveis não declaradas, e a variável entra na chave de cache). Os `inputs` de `lint`, `typecheck` e `test` ganham `drizzle.config.ts`. `dev` e `start` não entram no Turbo.
- **CI (Q11):**
  - `affected-areas.sh` ganha `[api]=apps/api/` no mapa por workspace; a área `api` também liga quando `infra/` muda, porque os testes dependem do compose;
  - novo job `api`, no molde do `packages` mais os passos de compose do `infra`: `docker compose up -d --wait` → `bun install --frozen-lockfile` → `bunx turbo run lint typecheck build test --filter=@caravan/api` → `down -v` com `if: always()`; `DATABASE_URL` no `env` do job;
  - o `ci` passa a depender de `api`.

**Alternativas descartadas:**

- **Só `src/db/`, sem Elysia** (primeira versão deste plano): o app nasceria sem servidor, e o item de auth teria de montar Elysia e Better Auth juntos.
- **`packages/db`:** quebraria a regra "nenhum pacote usa APIs do Bun" (o `Bun.sql`) e contradiria o §13.
- **Migration de base vazia e testes de migrations agora** (versão anterior deste plano): descartados pelo dono do projeto (Q3). Os testes ficam mais úteis sobre uma migration de verdade.
- **Criar todas as tabelas do §11 agora:** contraria a decisão do dono do projeto.
- **Testar as rotas subindo o servidor numa porta:** mais lento e sujeito a conflito de porta; o `app.handle` exercita o mesmo app.

## 6. Estratégia de testes e validação

- **Dá para rodar hoje, localmente:** Postgres do compose (`bun run infra:up`), Bun e Biome. Tudo de F1 a F3 roda na máquina.
- **Nível:** testes da API no seam REST documentado. `/healthz` e `/ready` são chamados via `app.handle`, com o cliente Drizzle real, contra o `caravan_test` ou contra uma porta sem Postgres. Nada é mockado.
- **Valores esperados independentes:** status e corpos HTTP literais (`200`/`503`, `ok`/`unavailable`).
- **Verificações negativas** (F2 e F3): o 503 com o Postgres fora do ar e a saída com erro sem `DATABASE_URL`. Vão para o PR com a saída observada.
- **Depende de algo futuro:**
  - o primeiro job `api` real na CI depende de push autorizado;
  - migrations e os três testes de migrations: item de auth (§10);
  - Redis no `/ready` (Q12), o 503 durante o shutdown e o binário compilado: itens previstos;
  - a verificação do D29 (Eden + OpenAPI com Zod): REST de trips.

## 7. Riscos e dependências

| Risco | Mitigação |
|---|---|
| Elysia sem LTS; a 2.0 é uma reescrita e está em RC (§2) | O app fica fino neste item (duas rotas), o que barateia a migração para a 2.0 depois. Acompanhar o lançamento da 2.0 e planejar a migração como item próprio |
| `/ready` travar se o Postgres aceitar a conexão e não responder | H4 cobre só "conexão recusada". Um timeout no `/ready` fica para o deploy, junto com o health check do Caddy (`/ready every 5s`) |
| `bun test` rodar arquivos em paralelo e dois deles usarem o `caravan_test` ao mesmo tempo (H6) | Verificar no F2. Se acontecer, o harness passa a usar um nome por arquivo (`caravan_test_<arquivo>`) |

- **Q4. Ciclo de vida do `caravan_test`:** criado no início e apagado no fim de **cada arquivo de teste** (`beforeAll`/`afterAll` do harness), começando por um `DROP ... IF EXISTS` para limpar execuções interrompidas.

  - O isolamento entre testes do mesmo arquivo (truncar as tabelas, transação com rollback, ou dados com IDs únicos) fica para o item de auth, com o primeiro teste que gravar dados.
- **Q8. `DATABASE_URL`:** obrigatória em todo lugar, inclusive nos testes, sem valor padrão no código. Localmente vem do `apps/api/.env` (copiado do `.env.example`); na CI, do `env` do job.
- **Q15. Nome do item:** o checkbox do `planner.md` passa a ser "**API (Elysia) + Drizzle**".

- **Checkbox de auth no `planner.md`:** passa a ser "Auth with Better Auth: email and password (no email sending) **+ first migration and migration tests**", para o compromisso do §10 ficar visível no roadmap. Os dois checkboxes já mudam no F0.

## 10. O que passa para o item de auth

Para não se perder, o plano do item "Auth with Better Auth" começa daqui:

- **Primeira migration:** as tabelas do Better Auth, geradas com `db:generate`, com o `user.locale` (D35) e IDs `DEFAULT uuidv7()` (D28).
- **Aplicação das migrations:**
  - `migrate()` com o migrator do Drizzle sobre `Bun.sql` (`drizzle-orm/bun-sql/migrator`) e uma conexão própria, separada do pool;
  - o script `db:migrate`, que o deploy vai chamar (`deploy.md` §5);
  - verificar se esse migrator funciona no `Bun.sql`. É parte da pergunta do spike do D30.
- **O harness do `caravan_test`** passa a aplicar as migrations depois do `CREATE`.
- **Os três testes de migrations** (`2.docker-compose.md` P5):
  1. as migrations aplicam do zero num banco vazio;
  2. o schema do Drizzle e as migrations batem;
  3. as migrations são só aditivas fora de uma fase de contração marcada.
- **Decisões que ficam abertas para lá**, com as recomendações deste plano:
  - **Q5. Marcação da contração:** recomendação, pelo nome da migration (`NNNN_contract_<motivo>`);
  - **Q6. O que conta como não aditivo:** além de `DROP`, `RENAME` e mudança de tipo, recomendo `SET NOT NULL` e `ADD COLUMN ... NOT NULL` sem `DEFAULT`;
  - **Q7. Sincronia schema × migrations:** recomendação, um teste com `drizzle-kit/api`;
  - **Q10. Seam dos testes de migrations:** recomendação, migrations aplicadas a um Postgres real e uma função pura para a política aditiva, registrados no `development.md` §2.
- **Biome:** ignorar `src/db/migrations/meta/**`, que o `drizzle-kit` gera com outra formatação.
- **Isolamento entre testes** do mesmo arquivo (Q4).
